How the CSV check works

The validator reads the first row, normalises header names and checks for core fields such as product_id, product_name and manufacturer, plus recommended fields for materials, suppliers, compliance and lifecycle information.

Example header

product_id,sku,product_name,gtin,manufacturer,country_of_origin,materials,supplier_ids,compliance_docs,repair_info,end_of_life_info

Why start with CSV?

CSV is not the final DPP architecture, but it is a practical bridge for manufacturers whose data is still spread across ERP exports, spreadsheets, supplier emails and PDFs.

  • Use stable IDs instead of relying on product names
  • Keep one meaning per column
  • Use controlled units and values
  • Reference documents consistently
  • Keep supplier IDs machine-readable

Frequently asked questions

What does the DPP CSV Validator check?

It checks the first CSV row as a header and compares it with a practical starter set of product-data fields.

Does a high score mean my CSV is legally DPP-compliant?

No. The score only measures starter data coverage. Final legal fields depend on the product-specific measure.

Can I use the CSV with a future DPP platform?

A clean portable CSV is a useful migration format, but every platform or sector schema may require different field names and structures.
