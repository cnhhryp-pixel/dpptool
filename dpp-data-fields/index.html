Why there is no universal DPP field list

ESPR defines the overall passport architecture, but product-specific measures decide which information is mandatory, who can access it and whether the passport applies at model, batch or item level. A practical data model should therefore separate reusable core fields from sector-specific extensions.

Core data layers

Master data

Product IDs, model/SKU, manufacturer, operator and classification information.

Evidence data

Materials, suppliers, declarations, test reports and technical documentation.

Lifecycle data

Durability, repair, spare parts, updates, recycling and end-of-life information.

Recommended internal architecture

Keep the internal source-of-truth richer than the public passport page. This lets you publish different views for consumers, professional actors or authorities while preserving one governed product record.

Prepare for mapping, not hard-coding

Field names and schemas will evolve by sector. Use stable internal meanings, controlled values and identifiers so data can be mapped into future DPP schemas without rebuilding the source system.
